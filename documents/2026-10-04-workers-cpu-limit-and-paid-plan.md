# 2026-10-04 Error 1102（CPU 時間の上限超過）の調査と、Workers 有料プランへの切り替え・Next.js からの作り直しの検討

- 対応日: 2026-10-04
- きっかけ: [公開ページの作り置き](./2026-10-04-static-like-caching.md)をデプロイしたあと、管理画面で記事を保存・公開すると「通信に失敗しました。時間をおいて再度お試しください。」と出た（アーカイブはできた）。テスト中に Cloudflare の「Error 1102 Worker exceeded resource limits」の画面も出た
- 決定: **Workers の有料プラン（Workers Paid）に切り替える**。2027年3月ごろに Next.js を使わない構成での作り直しを検討する

---

## 1. 何が起きていたか

### 1-1. 原因: 無料プランの CPU 時間の上限（1回 10ミリ秒）

本番のログ（`wrangler tail`）に `exceededCpu` が出ていた。Cloudflare Workers の**無料プランは、1回のリクエストで CPU を使える時間が 10ミリ秒**。超えると打ち切られ、訪問者には Error 1102（ページによっては 503）が返る。

- 打ち切りは毎回ではない。年表では 68・54・80ミリ秒の回は表示され、別の回は 10ミリ秒の時点で打ち切られた。どの条件で見逃し、どの条件で打ち切るかは公開されておらず、予測できない
- 上限は「CPU が計算している時間」で、Neon・R2・D1 の応答を待っている時間は数えない。**訪問者に待ってもらっても、Worker の計算量が同じなら打ち切られ方は変わらない**
- 管理画面の保存・公開は、保存に加えて移動先のページの組み立てまで1回で行うので重く、失敗しやすい。アーカイブが成功したのは、たまたま見逃された回だったと考えられる

### 1-2. 「急に」起きはじめた理由

- 前回のデプロイは 10月4日 2:09（日本時間）。そのあと 20:58 のデプロイまで一度もデプロイしておらず、**約15コミット分（デザインの統一、検索バー、サイト全体の UI/UX、年表のポップアップ、作り置きなど）がまとめて本番に出た**
- 作り置きで重くなった処理がある（最初の1回に作り置きを R2 へ保存する、公開時に移動先のページを作り置きにして D1 に記録する）。年表もポップアップ用に全出来事の本文を含めたので重くなった
- デプロイ直後は作り置きが空なので、各ページの「最初の1回」が集中した。確認作業で短時間に数百回アクセスしたことも重なった
- 一方で、Next.js のページを毎回組み立てると数十ミリ秒かかるので、**以前から 10ミリ秒は超えていた**はず。以前は見逃されていた超過が、今回の変更で目に見えるほど増えた、というのが一番ありそうな説明。昨日までのログは見られないため、以前どれくらい打ち切られていたかは確かめられていない

### 1-3. よくある誤解: 「以前はブラウザで組み立てていた」ではない

以前も、ページは**毎回 Worker（サーバー側）で組み立てていた**。作り置き（ISR）は「最初の1回だけ組み立て、以降は作り置きを返す」変更で、Worker の仕事を**減らす**もの。実際に記事ページの CPU 時間は 50ミリ秒前後から 3〜6ミリ秒に下がった。

## 2. どこで CPU 時間を使っているか（計測結果）

### 2-1. 本番での1回あたりの CPU 時間（`wrangler tail` の `cpuTime`）

| ページ | 何をしているか | CPU 時間 | 打ち切り |
|---|---|---|---|
| 記事ページ（HTML 約 35KB） | 作り置きを返す | **3〜6ms** | なし |
| トップ・経歴（HTML 約 200KB） | 作り置きを返す | **7〜14ms** | ときどき |
| 記事一覧 | 毎回組み立てる | **24〜121ms** | ときどき |
| 年表（HTML 約 270KB） | 毎回組み立てる | **52〜105ms** | ときどき |
| 年表の詳細（形式が不正な id） | 404 を組み立てる | 16〜30ms | — |
| 存在しない記事（毎回違う URL） | 404 を組み立てて保存 | 10〜57ms | ときどき |
| 起動直後の Worker の最初の1回 | プログラムの読み込み＋組み立て | 50〜90ms 前後（記事ページ 87ms、サイトマップ 88ms など） | ときどき |
| 管理画面の保存・公開 | 保存＋移動先のページの組み立て＋作り置きを捨てる | 未計測（ログインが必要） | 失敗していた |

### 2-2. 組み立ての内訳（手元の Node.js で `next start` を動かし、CPU プロファイルを記録）

本番の Worker の中は細かく記録できないため、同じページを Node.js で動かして内訳を見た。Node.js の方が全体に3〜4倍速いが、割合は参考になる。

| ページ | 1回の CPU 時間（Node.js） | 内訳 |
|---|---|---|
| 記事一覧 | 9.1ms | React での組み立て 48%、データの受け渡し（ストリーム） 28%、アプリのコード 12% |
| 年表 | 15.3ms | React での組み立て 49%、ストリーム 20%、メモリの片付け（GC） 16% |
| 記事ページの初回 | 29.1ms | ストリーム 30%、アプリのコード（Markdown の変換など） 25%、React 22%、GC 11% |
| 記事ページの2回目以降 | 2.1ms | 作り置きを返すだけ |

本番の Worker では、OpenNext の変換処理や作り置きの読み込み・JSON 変換が加わり、Node.js の3〜4倍になっていると考えられる。

**計測方法のメモ**: 手元の Worker 環境（`opennextjs-cloudflare preview`）でも開発者ツールのプロトコルで CPU プロファイルを取れる（`--inspector-port`、接続時に `Origin: https://devtools.devprod.cloudflare.dev` が必要）。ただし R2・D1 の代わりをする処理が同じ場所で動くので、記録にストレージ側の処理が大きく混ざり、内訳には使えなかった。内訳は Node.js の `next start` に `--inspect` を付けて取った（`next start` は実際の処理を子プロセスの next-server で行うので、そちらの接続口に接続する）。

### 2-3. 分かったこと

1. **一番大きいのは、React でページを組み立てる処理**。記事一覧・年表はアクセスのたびに組み立てるので、毎回 20〜100ミリ秒かかる
2. **年表はページが大きい**（約 270KB。多くはポップアップ用の全出来事の本文）ので特に重い
3. **トップ・経歴は、作り置きを返すだけでも上限ぎりぎり**。HTML が約 200KB あり、返すときに HTML 全体を読み込んで目印（etag）を計算するので、大きさに比例して CPU を使う
4. **起動直後の Worker の最初の1回は、どのページでも重い**（その場で必要なプログラムを読み込むため）。Cloudflare の Worker は頻繁に入れ替わるので避けられない
5. ミドルウェア（ログインの確認）は管理画面と画像アップロードだけで動く設定で、公開ページの CPU 時間には関係しない

## 3. 各ページのレンダリング方式（2026-10-04 時点）

### 3-1. 公開ページ

| ページ | 方式 | いつ組み立てるか | Neon を読むとき |
|---|---|---|---|
| トップ・経歴・受賞歴・資格 | 静的（`○`） | デプロイ時のビルドで1回だけ。デプロイ時に R2 に入る | 読まない（内容はコードに直接書いてある）|
| 記事ページ `/{blogs,products,books}/[slug]` | ISR（`●`。初回アクセス時に作って保存） | 公開後（またはデプロイ後）の最初のアクセスで1回。R2 に保存し、以降は OpenNext がそのまま返す | 作るときだけ |
| 記事一覧 `/blogs` など | 動的（`ƒ`）＋データだけ作り置き | アクセスのたびに組み立てる（タグ・ページ番号を URL の検索パラメータで受けるため）| 作り置きが捨てられた後の最初の1回だけ |
| 年表 `/history` | 動的＋データだけ作り置き | アクセスのたびに組み立てる（並び順 `?order=` を受けるため）| 同上 |
| 年表の詳細 `/history/[id]` | 動的＋データだけ作り置き | アクセスのたびに組み立てる | 同上 |
| サイトマップ | 静的（作り直しあり） | ビルド時に作り、記事・年表の保存で捨てられたら次のアクセスで作り直す | 作り直すときだけ |
| 自動生成のサムネイル `/api/og` | 動的＋Cloudflare の Cache API | 拠点ごと・タイトルごとの最初の1回だけ画像を生成し、その拠点に保存 | 読まない |
| 画像 `/api/images/[key]` | 動的 | 毎回 R2 から読んで返す（ブラウザには1年キャッシュ）| 読まない |

### 3-2. 管理画面

- すべてのページが動的（`force-dynamic`）で、毎回 Neon を読んで組み立てる
- 保存・公開・アーカイブなどは Server Action
- 管理画面へのアクセスでは、最初にミドルウェアがログインを確認する

## 4. 記事を公開してからの流れ

### ① 「公開」を押したとき

```
ブラウザ ─(公開ボタン)→ Worker
 1. ミドルウェア: ログインの確認
 2. publishAction（Server Action）
    a. 入力の確認（Zod）
    b. Neon: 保存済みの slug を取得（slug は変更不可）
    c. Neon: 記事を「公開中」として保存、タグの付け直し
    d. 作り置きを捨てる記録を D1 に書く
       ・その記事のページ（revalidatePath）
       ・記事一覧・件数・タグ・公開中の slug 一覧のデータ（updateTag）
       ・サイトマップ（revalidatePath）
    e. 記事ページへ移動（redirect）
 3. 移動先の記事ページを、同じ1回の処理の中で組み立てる
    ・「記事があるか」の確認（slug 一覧の作り置きが捨てられているので Neon を読む）
    ・記事本文とタグを Neon から読み、Markdown を変換して組み立てる
    ・できたページを R2 に保存（新しい作り置き）
 4. ブラウザに記事ページが表示される
```

この1回に処理が集中するので、CPU 時間がもっとも重い。Error 1102 や「通信に失敗しました」は、ここで上限を超えたもの。

### ② 公開後、訪問者が記事ページを開いたとき

R2 に作り置きがあり、D1 で捨てられていないことを確認できたら、そのまま返す（3〜6ms）。Neon は読まない。

### ③ 公開後、最初に記事一覧を開いた人

ページは毎回組み立てる。データの作り置きが捨てられているので、Neon からタグ一覧・記事一覧・件数を読み、R2 に保存する。2人目以降はデータを R2 から読む（ページの組み立ては毎回行う）。

### ④ 公開後、最初にサイトマップを読んだ検索エンジン

Neon を読んで作り直し、R2 に保存する。

### ⑤ 影響しないページ

トップ・経歴・受賞歴・資格・年表は、記事の公開では作り直さない。

### ほかの操作

| 操作 | 捨てる作り置き | 移動先 |
|---|---|---|
| 下書き保存 | 公開と同じ（公開中の記事を下書きに戻した場合に、公開ページから消すため）| 管理画面の一覧 |
| アーカイブ | 公開と同じ | 管理画面の一覧 |
| タグの名前・画像の変更、削除 | すべてのページ＋記事一覧のデータ | （画面はそのまま）|
| タグの作成・並べ替え・ジャンルへの追加/除外 | 記事一覧のデータ | （画面はそのまま）|
| 年表の出来事の保存・削除、ラベルの名前変更・削除 | 年表のデータ＋サイトマップ | 管理画面の年表一覧 |

## 5. 検討した対処と、有料プランにした理由

| 方法 | 内容 | 判断 |
|---|---|---|
| **A. 有料プラン（Workers Paid、月 5ドル〜）** | CPU 時間の上限が 30秒になる。コードの変更は不要 | **採用** |
| B. ブラウザで組み立てる | Worker はデータと空の画面だけ返す | 不採用: サイトのほぼ全面的な作り直し。検索エンジン向けの表示が弱くなる。起動直後の打ち切りは残る |
| C. 公開時に静的なサイトとしてビルドし直す | 公開ページは静的なファイルとして配信する（Worker を動かさない）| 不採用（今は）: 自動デプロイの仕組みと大きな作り変えが必要。管理画面の打ち切りは残る |
| D. 記事一覧・年表もページごと作り置きにする | 公開ページの多くが 3〜10ms 程度になる見込み | 今は見送り（有料プランにした後でも速度・料金の改善になるので、将来の候補）|

B・C・D のどれでも、**管理画面の保存・公開と、起動直後の Worker の打ち切りは、無料プランでは完全には避けられない**（Next.js のアプリは起動するだけで 10ミリ秒を超えることがある。静的な経歴ページでも起動直後に打ち切られていた）。CMS として保存・公開が確実にできることが欠かせないので、有料プランにした。

### ISR（作り置き）は必要か（検討メモ）

- **必須ではない**。入れた目的のうち「Neon の無料枠を使い切らない」は、実際の使用量を確かめずに進めた見込みだった
- 有料プランでは、作り置きがなくても動く。残す理由は「Neon の負担を減らす」「表示を速くする」「CPU 時間（料金）を減らす」
- 負担: 作り置きを捨て忘れると古いページが出続ける。R2・D1・OpenNext の設定が増え、Next.js と OpenNext の細かい挙動に左右される（例: [`STALE` の問題](./2026-10-04-static-like-caching.md#8-デプロイ後の確認と見つかった問題記事ページが新しい-worker-で作り直されていた)）
- 当面は残して様子を見る。Neon のコンソールの Usage（今月の CU 時間）と、Cloudflare の1日のリクエスト数を見て、外すかどうかを判断する

## 6. 有料プランで得られるもの

料金は月 5ドルからで、月 1,000万リクエストと CPU 3,000万ミリ秒が含まれる（超えた分は 100万リクエストごとに 0.30ドル、CPU 100万ミリ秒ごとに 0.02ドル）。このサイトの規模なら 5ドルを超えることはまずない。

### 6-1. すぐ効くもの

| 変わること | 無料 → 有料 | このサイトへの効果 |
|---|---|---|
| **1回の CPU 時間の上限** | 10ミリ秒 → 30秒（最大5分）| Error 1102、保存・公開の失敗、記事一覧・年表の 503 がなくなる。**今回の問題の本命** |
| 1回の処理の中で外へ出せる通信の数 | 50回 → 10,000回 | Neon・R2・D1 への問い合わせはそれぞれ1回と数える。公開ボタン1回で十数回なので、余裕が大きくなる |
| Workers Logs（ログ）の量 | 1日 20万件 → 月 2,000万件 | 調査がしやすくなる |
| Hyperdrive | 1日 10万回 → 無制限 | 6-3 を参照 |

### 6-2. CPU に余裕ができて、安心して使えるもの

- **自動生成のサムネイル（`/api/og`）**: タイトルから画像を描く処理はとても重い。無料プランでは、拠点ごとの最初の1回が打ち切られていた可能性がある（未確認）
- **管理画面の処理**: 公開時に移動先のページを組み立てても打ち切られない
- 今後の機能（コードの色分け表示、サイト内検索など）も、CPU を気にせず足せる

### 6-3. 今後使えそうなもの（必要になったら）

- **Hyperdrive**: Neon への接続をまとめて使い回し、読み取りの結果も短時間キャッシュする。管理画面や動的なページで、Neon への問い合わせが速くなる。ただし、Neon の起きている時間を減らす効果は、今の作り置きの方が大きい
- **Cron Triggers**（決まった時刻に処理を動かす。無料 5個 → 有料 250個）: デプロイ直後に主要なページを先に作っておく（作り置きの温め）など
- **Queues**（後で処理する順番待ち）: 公開時の重い処理を後回しにして、ボタンの反応を速くするなど

### 6-4. 課金しても変わらないもの

- Worker の起動時間の上限（1秒）、メモリ（128MB）
- R2・Neon の料金（別のサービス）
- 起動直後の最初の1回が重いこと（打ち切られなくなるだけで、表示が少し遅いのは同じ）

## 7. 2027年3月ごろに Next.js を使わずに作り直す場合に大変なところ

2026-10-04 時点のコードの規模は、ページ 28、部品 46（うちブラウザで動くもの 19）、Server Action のファイル 5。Next.js の機能を使っている箇所は、画面遷移（`next/navigation`）19、リンク（`next/link`）15、ほかに `next-auth`・`next/og`・`next/font`・`next/dynamic` など。デプロイするプログラムの大きさは 12.9MB（圧縮後 2.9MB）。

### 7-1. 特に大変そうなところ

1. **認証（GitHub ログイン）の置き換え**: `next-auth`（Auth.js v5）は Next.js 前提の作り。別の認証ライブラリに替えるか、**Cloudflare Access**（Cloudflare 側で `/admin` の前に GitHub ログインを置く仕組み。少人数なら無料）を使って認証のコード自体をなくすか。どちらでもセキュリティに直結するので確認に時間がかかる
2. **Server Action を API に置き換える**（保存・公開・アーカイブ・タグ・年表・日記）: Next.js が自動でやっていた次の処理を自分で作る必要がある
   - 他サイトからの不正な送信を防ぐ確認
   - 送信後の画面の更新
   - 移動（redirect）
3. **「公開したら反映される」仕組みを自分で作る**: 今は ISR と `revalidatePath` / `updateTag`、OpenNext の作り置きで実現している。今回見つかった問題（`STALE`、404 のステータス、捨て忘れのリスク）もこのあたりだった。たとえば「公開時にページの HTML を作って R2 に置く」形に設計し直す。どの操作でどのページを作り直すかの対応表（4章）はそのまま使える
4. **画面遷移の体験を作り直す**: Next.js はリンク先の先読み、ページ全体を読み直さない移動、読み込み中の表示（`loading.tsx`）、絞り込み中に一覧を薄くする表示などを担っている。なくなると、毎回ページ全体を読み直す普通のサイトになる。今の操作感をどこまで再現するかを決める必要がある
5. **SEO 周りを同じにする**: 次のものを、URL・ステータス・中身を変えずに作り直す必要がある。URL が1つでも変わると、検索結果や共有されたリンクが切れる
   - 記事ごとの OGP（`generateMetadata`）
   - サイトマップ
   - 自動生成のサムネイル（`next/og`）
   - 存在しない URL の 404

### 7-2. そのまま使えるもの

- Drizzle（DB）、Zod（入力の確認）、Tailwind CSS、R2 の画像と画像配信の処理
- React の部品（React を使う構成なら）: エディタ（EasyMDE）、dnd-kit の並べ替え、ダイアログの共通フック
- DB のデータ・R2 の画像（移行は不要）

### 7-3. 進め方の提案

- **最初に構成を決める**: React の部品を活かすなら、React を使える構成（Astro＋React の部品、React Router など）を選ぶと、作り直す量がかなり減る。このサイトは「たまに更新する CMS ＋ほぼ静的な公開ページ」なので、次の分け方が合っていそう
  - 公開ページ: 公開時に HTML を作って置く
  - 管理画面: 小さなアプリと API
- **作り直す前に、今の動きを確認項目にしておく**: 自動テストがないので、今の挙動（URL・ステータス・OGP・管理画面の各操作）を確認項目かブラウザでの自動テストにしておくと、作り直した後に同じ動きかを確かめやすい。CLAUDE.md と documents の記録が土台になる
- **切り替えは並行で**: DB と画像はそのまま使えるので、新しいものを別の URL で動かして確かめてから、ドメインを切り替える
- **Next.js をやめると軽くなるもの**: OpenNext の変換処理がなくなり、プログラムも小さくなるので、起動直後の重さと1回の CPU 時間が減る見込み

## 8. 残っていること

- **有料プランへの切り替え**（Cloudflare のダッシュボード → Workers & Pages → Plans）。切り替え後に、本番のログで `exceededCpu` がなくなったことと、管理画面の保存・公開ができることを確かめる
