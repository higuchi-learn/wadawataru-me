# 2026-10-04 一覧ページへ移るときに画面が固まって見える問題

- 対応日: 2026-10-04
- 対象: 制作物（`/products`）・ブログ（`/blogs`）・読書記録（`/books`）の一覧ページ

## 概要と原因

### 症状

しばらくサイトを開いていなかったあとで、ヘッダーの「制作物」を押すと、**2秒以上なにも反応せず（固まったように見え）**、その後に一覧ページへ切り替わる。一方、Ctrl+Shift+R（キャッシュを無視した再読み込み）で一覧ページを開いたときは、遅いとは感じない。

### 原因1: 待っている間に何も表示していなかった

ヘッダーのボタンは `next/link` なので、押してもページを丸ごと読み込み直すのではなく、**今の画面を表示したまま、裏で次のページのデータ（RSC ペイロード）をサーバーに取りに行く**。

一覧ページは、アクセスのたびにサーバーで DB を引いて描画するページ（ビルド結果で `ƒ Dynamic`）。しかしプロジェクト内に `loading.tsx`（読み込み中の表示）が1つもなかった。そのため、Next.js はデータが届くまで前の画面を出し続け、**ボタンを押しても画面が一切変わらない**状態になっていた。

Ctrl+Shift+R の場合は、ブラウザ自身が読み込み中の表示（タブのくるくるなど）を出すので、「固まった」とは感じにくい。

### 原因2: 休止明けの最初の1回だけ、サーバー側の処理に時間がかかる

しばらくアクセスがないと、次のものが休止する。休止明けの最初のアクセスだけ、それを起こす時間が上乗せされる。

- **DB（Neon、シンガポール）**: 無料プランでは、一定時間アクセスがないとコンピュートを休止する。
- **Worker**: 本体（OpenNext のサーバー処理）が約 7.6MB あり、休止明けは読み込み直しが必要になる。

さらに一覧ページは、DB とのやり取りが2往復ある（タグの取得 → 記事一覧と件数を並列で取得）。

本番での実測:

| | 応答開始までの時間 |
|---|---|
| デプロイ直後の初回 | 約 1.7秒 |
| 2回目以降 | 約 0.38秒 |
| DB を使わない静的ページ（`/career`）| 約 0.2〜0.3秒 |

7分あけて測った回は再現しなかった（休止までの時間が7分より長いためと考えられる）。そのため、DB と Worker のどちらが主な原因かまでは切り分けられていない。

### 方針

このサイトはアクセスが頻繁ではないので、**休止明けの初回が遅くなること自体は受け入れる**（DB の休止を止めるには Neon の有料プランが必要になる）。そのうえで、**待っている間に画面が固まって見える**ことを直す。

## 放置するとどうなるか

- ボタンを押しても反応がないので、訪れた人は「壊れている」「押せていない」と感じて、何度も押したり、ページを離れたりする。
- ポートフォリオとして見てもらう場面（就職活動・交流）で、久しぶりに開いた人ほどこの症状に当たりやすい。第一印象が悪くなる。

## どう対処したか

### 1. 一覧ページに `loading.tsx` を追加した

`loading.tsx` を置くと、Next.js はそれを同じフォルダの `page.tsx` の Suspense の fallback として扱う。ページの切り替え時に**すぐに表示し、データが届いたら本物に差し替える**。また `<Link>` の先読み（prefetch）で、この読み込み中の表示が事前に取得されるので、**ボタンを押した瞬間に画面が切り替わる**。

表示する内容は [`src/components/PostListSkeleton.tsx`](../src/components/PostListSkeleton.tsx) に作り、3ジャンルの `loading.tsx` から使っている。

- **見出し帯（`PageHero`）は本物をそのまま出す**: ジャンル名と説明は DB を使わずに決まる。読み込みが終わっても見出しが動かず、カード部分だけが差し替わるので、画面のガタつきが少ない。
- **検索バー・ページ送り・カード4枚を灰色の箱にする**: カードは本物の `Card` と同じ外枠・幅・並べ方にして、差し替え時にレイアウトが大きく動かないようにした。
- **アクセシビリティ**: 領域に `aria-busy="true"` を付け、読み上げ用に「読み込み中です」（`role="status"`、画面には出さない `sr-only`）を置いた。点滅アニメーションは `motion-safe:` にして、OS で「視差効果を減らす」を設定している人には出さない。

### 2. 一覧ページを route group `(list)` に移した

`loading.tsx` を `products/` の直下に置くと、**記事の詳細ページ（`products/[slug]`）へ移るときにも一覧用の骨組みが出てしまう**（`loading.tsx` は、そのフォルダより下のすべてのページに効くため）。

そこで、一覧の `page.tsx` だけを、URL に影響しない route group の `(list)` フォルダに移し、`loading.tsx` もそこに置いた。

```
src/app/(public)/products/
├─ (list)/
│  ├─ page.tsx      ← 一覧（URL は /products のまま）
│  └─ loading.tsx   ← 一覧にだけ効く
└─ [slug]/
   └─ page.tsx      ← 詳細（骨組みの影響を受けない）
```

`/blogs`・`/books` も同じ構成にした。

### 3. 英字ラベルを共通の場所に移した

見出し帯の英字ラベル（`Products` / `Blog` / `Books`）を `PostListPage.tsx` の中から [`GenreAbout.tsx`](../src/components/GenreAbout.tsx) の `GENRE_LABEL_EN` に移した。一覧ページ本体と読み込み中の表示の両方で使うため。

## 確認したこと

| 確認 | 結果 |
|---|---|
| `tsc` / `pnpm lint` / `next build` | エラーなし。URL（`/products`・`/blogs`・`/books`）は変わっていない |
| `pnpm preview` で一覧ページの HTML を取得 | 読み込み中の表示（`<template id="B:0">`）が先に送られ、そのあと本物の内容（`<div hidden id="S:0">`）が届いて差し替わる流れになっている。記事カードの数は以前と同じ |
| 詳細ページ（`/products/bingo2`・`/blogs/portfolio`）| 読み込み中の表示は含まれない（route group が効いている）|

**未確認**: 実際のブラウザでの見た目（骨組みのレイアウトが本物のカードとどれくらい揃っているか）と、休止明けに「制作物」を押した瞬間に骨組みへ切り替わること。デプロイ後に、しばらく時間を空けてから確かめる必要がある。

## 追加対応: 骨組みのカードと本物のカードの大きさがずれていた

### 概要と原因

読み込み中の骨組みのカードと、読み込み後に表示される本物のカードの大きさが一致せず、切り替わるときに違和感があった。原因は2つ。

1. **骨組みのカードを、本物の `Card` の構造をなぞらずに作っていた**: だいたいの見た目で灰色の箱を並べていたので、各行の高さが本物と違っていた。本物はタイトル 28px・説明文（画面幅ごとの固定の高さ）・タグ 26px・日付 16px の行で高さが決まり、スマホ幅では外枠に余白がない。骨組みは別の余白（`gap`・`pb-3`）を持っていた。ページ送りも、本物は高さ 20px で上下に2つあるのに、骨組みは高さ 24px が1つだけだった。
2. **骨組み全体を包む要素に `items-center` が付いていた**: そのせいで中の `<main>` が画面幅いっぱいに広がらず、中身の幅まで縮んでいた。本物のページでは `<main>` が幅いっぱいに広がり、カードはその幅を基準に `w-full` で広がる。骨組みのスマホ幅のカードは、本物より狭くなっていた。

### 放置するとどうなるか

- 読み込みが終わった瞬間にカードの大きさや位置が変わり、画面がガタつく（レイアウトシフト）。骨組みを出す目的（待ち時間を自然に見せる）が損なわれる。
- 骨組みの寸法を本物から書き写す作り方のままだと、カードの見た目を変えたときに骨組みだけ古い寸法で残り、同じずれが再発する。

### どう対処したか

- **`Card`・`CardList` のクラスを定数として書き出した**（[`Card.tsx`](../src/components/Card.tsx) の `CARD_CLASS`・`CARD_BODY_CLASS`・`CARD_TEXT_CLASS`・`CARD_DESCRIPTION_CLASS`・`CARD_THUMBNAIL_CLASS`、[`CardList.tsx`](../src/components/CardList.tsx) の `CARD_LIST_CLASS`・`CARD_WIDTH_CLASS`）。本物のカードの見た目は変えていない。
- **骨組みのカードを、本物と同じ構造・同じ定数で組み直した**。文字の行は「本物の行と同じ高さの枠」の中に、それより少し低い灰色の箱を置く形にした。こうすると、枠の高さが本物と一致する。今後カードの見た目を変えても、骨組みは自動で追従する。
- **スマホ幅の説明文だけは、よくある2行分（32px）の高さにした**: 本物はスマホ幅だけ説明文の高さが固定されておらず、文の長さで決まるため、完全には一致させられない。sm 以上の幅では本物と同じ固定の高さになる。
- 包む要素の `items-center` を外し、ページ送りも本物と同じ高さ 20px・上下2つにした。

### 確認したこと

`pnpm preview` で `/products` を開き、ヘッドレスの Chrome で「骨組み」と「本物」を同じ幅で撮って並べて比べた。骨組みは、HTML から `<script>` を取り除いて、差し替えが起きない状態で撮影した。

| 幅 | 結果 |
|---|---|
| 1280px（2列） | カードの幅・高さ・位置が一致。検索バー・ページ送りの位置も一致 |
| 390px（スマホ・1列） | 各カードの高さと開始位置が一致（説明文が2行のカードの場合） |

> **訂正**: 当初ここに「390px 幅では検索バーと見出しの説明文が画面の右端からはみ出している」と書いたが、**撮影方法の誤り**だった。Windows のヘッドレス Chrome は、ウィンドウ幅を 390px に指定しても約 500px 幅で描画し、スクリーンショットだけを左 390px で切り取っていた。そのため、右側が切れてはみ出しているように見えた。また、この 390px での比較も、実際には約 500px 幅（sm 未満なのでスマホと同じレイアウト）での比較だった。正しく測り直した結果は、次の「スマホ幅の表示の修正」に書いた。

## 追加対応: スマホ幅の表示の修正

### 概要と原因

1. **365px より狭い画面で検索バーがはみ出す**: 一覧ページの検索バーは幅 365px 固定で、親要素は左右に 16px の余白を持ち、中央寄せになっている。画面幅を W とすると、検索バーの右端は (W + 365) / 2 の位置になる。390px・375px では画面内に収まるが、**360px では右に 2.5px、320px では左右に 22.5px ずつはみ出す**。
2. **スマホのカードの区切りが分かりにくい**: スマホ幅のカードには枠線も影もなく、下の余白もない。そのため、日付の行のすぐ下に次のカードのサムネイルが続き、どこまでが1枚のカードか分かりにくかった。

### 放置するとどうなるか

- 1: 画面が横にスクロールできてしまい、縦にスクロールしようとしたときに画面が左右にぶれる。320px のときは、検索バーの左端（入力欄の先頭）が画面の外に切れて見えなくなる。
- 2: 記事の一覧を流し読みするときに、どのタイトルがどの画像のものか分かりにくい。

### どう対処したか

| 対象 | 変更 |
|---|---|
| 検索バー（[`PostListPage.tsx`](../src/components/PostListPage.tsx)） | `max-w-full` を追加。親の幅（画面幅 − 左右の余白）までは縮むようにした |
| カードの下の余白（`CARD_CLASS`） | スマホ幅だけ `pb-10`（40px）を追加（最初は 10px にしたが、少なすぎたため 40px に広げた）。sm 以上は従来どおり `sm:pb-2`（枠線と上下 8px の余白がある） |

カードの下の余白は `CARD_CLASS` に入れたので、読み込み中の骨組みにも自動で同じ余白が付く。

**カードのデザインは変えていない**: 骨組みとそろえるためにカードのクラスを定数に書き出したが、変更前と同じクラスをそのまま移しただけ。変更前のコミットとクラスを1語ずつ比べ、違いは追加した `pb-10`（当時は `pb-2.5`）と `sm:pb-2` だけであることを確認した（`sm:pb-2` は、もともとの `sm:py-2` と同じ 8px。タブレット以上で余白が変わらないことを明示するために付けた）。

> **取り消した変更**: 320px 幅でカードの日付の行（「公開日 : …　最終更新日 : …」、行全体が `whitespace-nowrap`）が右にはみ出すため、いったん「狭いときは2行に折り返す」形に変えた。しかし、これはカードのデザインの変更にあたり、依頼の範囲を超えていたので元に戻した。この問題は未対応として残している。

### 確認したこと

最初の計測（ページの幅を CSS で固定して測る方法）では、検索バーが JavaScript で描画される部品のため、画面に出ておらず測れなかった。そこで、**幅を指定した iframe の中にページを表示**して撮影した。iframe の中では JavaScript も動き、メディアクエリも iframe の幅で判定されるので、実機と同じ条件になる。

| 幅 | 結果 |
|---|---|
| 320px | 検索バーが余白の内側に収まった。カードの下に余白が入った。ただし日付の行のはみ出しは残る（上記のとおり未対応） |
| 360px・390px | 検索バーが収まった。カードの下に余白が入った |
| 768px | カードは枠線つきの従来の見た目のまま（変化なし） |

**別に見つかった既存の問題（対応しないと決定）**:

- 320px 幅では、ヘッダー右上の X のアイコンとメニューボタン（≡）が重なっている。
- 320px 幅では、カードの日付の行が右にはみ出す。

どちらも 360px 以上では起きない。**スマホは 360px 以上を対応範囲とする**と決めた（今よく使われている機種は Android が 360〜412px、iPhone は最小でも 375px。320px は主に 2016 年以前の機種の幅で、iPhone の「画面表示の拡大」や一部の折りたたみスマホのカバー画面でしか使われない）。360px 未満は、内容が読めて操作できれば十分とする。

## 追加対応: 1024〜1028px でカードが2列にならない

### 概要と原因

画面幅 1024〜1028px で、一覧のカードが2列にならず、幅 500px のカードが中央に1列で並んでいた（1029px 以上なら2列になる）。

lg（1024px）以上では、カードを幅 500px にして2列に並べる。2枚並べるには、500 × 2 ＋ 間隔 6px（`lg:gap-1.5`）＋ 一覧の左右の余白 4px × 2（`sm:p-1`）＝ **1014px** が必要だった。

ところが、Tailwind のブレークポイント（CSS のメディアクエリ）は**スクロールバーを含めた画面幅**で判定される。一方、カードを並べられるのは**スクロールバーを除いた幅**で、Windows では 15〜17px 狭くなる。1024〜1028px のときに使える幅は 1007〜1013px しかなく、1014px に届かないため、2枚目が次の行に落ちていた。「ブレークポイントの値＝使える幅」として固定幅を組んでいたことによるズレ。スクロールバーが重なって表示される環境（Mac など）では起きない。

### 放置するとどうなるか

- Windows で画面幅がちょうどこの範囲のとき（ウィンドウを左右に分割したときなど）、カードが中途半端な幅で1列に並び、レイアウトが崩れて見える。

### どう対処したか

[`CardList.tsx`](../src/components/CardList.tsx) の `CARD_LIST_CLASS` に `lg:px-0` を追加し、2列表示（lg 以上）のときだけ一覧の左右の余白をなくした。2列に必要な幅は **1006px** になり、スクロールバーが 17px あっても 1024px で収まる（使える幅 1007px）。

検討した他の案:

| 案 | 採用しなかった理由 |
|---|---|
| 2列にする幅を 1040px に遅らせる | Tailwind 標準にないブレークポイントが増え、ほかの部品（ヘッダーのナビなど）と切り替わる幅がずれる |
| 2列のときのカード幅を可変にする | カードのデザインに手が入る |

- ブレークポイントは Tailwind 標準の `lg` のまま変えていない。カードのデザインも変えていない。
- 読み込み中の骨組みも同じ定数を使っているので、一緒に直る。
- **注意点**:
  - 1024px 付近では、カードが画面の左右の端にほぼ接する（すき間 1〜3px）。
  - 余裕は 1px しかない。スクロールバーが 17px より太い環境では、まだ足りない可能性がある。

### 確認したこと

スクロールバーが出る状態のヘッドレス Chrome で撮影した。

| 幅 | 結果 |
|---|---|
| 1023px | タブレットと同じ1列（幅 600px）。lg の手前なので意図どおり |
| 1024px | 2列になった |
| 1026px | 2列になった |

## 残っていること・関連して分かったこと

- **詳細ページ（`/products/[slug]` など）にも同じ症状が出うる**: 詳細ページも毎回 DB を引く。トップページや一覧のカードから詳細へ移るときも、休止明けは固まって見える可能性がある。必要なら、詳細ページ用の骨組みを `[slug]/loading.tsx` に追加する。
- **画像配信（`/api/images`）がエッジにキャッシュされていない**: [一括修正の項目3](./2026-10-03-maintenance.md#3-画像配信にキャッシュ指定がなかった)では「`Cache-Control` を付ければ Cloudflare のエッジにキャッシュされる」と書いたが、誤りだった。Worker が返したレスポンスは、ヘッダーだけではエッジにキャッシュされない（[OG 画像の対応記録](./og-image-caching-fix.md)にあるとおり、Cache API を明示的に使う必要がある）。効いているのはブラウザのキャッシュだけで、初めて見る人には毎回 Worker と R2 が動いている（本番で 0.3〜1.1秒）。`/api/og` と同じく Cache API を使えば改善できる。
- **DB とのやり取りを1往復にまとめる**: タグの取得と記事一覧の取得を1回のクエリにまとめれば、毎回の待ち時間が少し縮む。
