# 2026-10-04 公開ページの「作り置き」（アクセスのたびに DB を読まない）と slug の固定

- 対応日: 2026-10-04
- きっかけ: 「CMS で記事や年表を公開した時点で、アクセスのたびに DB から取得せず、静的なサイトと同じように動かせないか」という相談
- 関連: [サイト全体の UI/UX 改善](./2026-10-04-site-wide-uiux.md)（その作業中に、DB への問い合わせ回数が気になったのが始まり）

この文書は、相談の流れ（何が問題か → どう解決するか → 何が心配か）と、実際にやったこと・確かめたことを、あとから振り返れるようにまとめたもの。

## 1. 何が問題だったか

### 1-1. アクセスのたびに Neon（DB）に問い合わせていた

記事ページ・記事一覧・年表は、誰かが開くたびに Worker が Neon から記事を読み、ページを一から作っていた。同じ記事を100人が見れば、同じ内容を100回読む。

原因は、OpenNext に「作ったページの保存先（キャッシュ置き場）」を設定していなかったこと（`open-next.config.ts` の R2 の行がコメントアウトのままだった）。保存先がないので、作ったページを取っておけない。

### 1-2. その結果、Neon の無料枠を使い切るおそれがあった

Neon の無料枠は、問い合わせの回数ではなく**起きていた時間**（月 100 CU 時間）で決まる。

- アクセスがあると起き、5分間アクセスがないと休止する
- 5分おきより頻繁にアクセスが続くと休めない。最小 0.25 CU で1日中起きていると、0.25 × 24時間 × 30日 = 約 180 CU 時間になり、無料枠を超える
- 検索エンジンのクローラーなど、人以外のアクセスも同じように数えられる
- 使い切ると**翌月まで DB が止まり、記事が表示できなくなる**（データは消えない）

### 1-3. 休止明けの表示が遅い

Neon が休止しているときの最初のアクセスは、起きるのを待つ分だけ遅い。以前 `loading.tsx` で「固まって見える」問題は和らげたが、待ち時間そのものは残っていた。

### 1-4. 管理画面の一部が、ビルド時の内容で作られていた（表に出ていなかった問題）

前のビルドでは `/admin/tags`・`/admin/diary`・`/admin/history/create`・`/sitemap.xml` が、ビルド時に DB を読んで静的なページとして作られていた。保存先がないので毎回作り直され、問題になっていなかった。保存先を有効にすると、**ビルド時の内容のまま固まる**（タグを追加しても管理画面に出ない、など）。

### 1-5. slug（URL パス）を変えても保存されていなかった（相談の途中で見つけた不具合）

記事エディタでは「URLパス」を書き換えられたが、既存の記事を更新する関数（`updatePostById`）は slug を受け取らず、書き換えていなかった。一方で、重複チェックと公開後の移動先には新しい slug を使っていた。

| 操作 | 起きていたこと |
|---|---|
| 公開済みの記事の slug を変えて「公開」 | DB は古い slug のまま。新しい URL へ移動して **404** |
| 下書きの slug を変えて「下書き保存」 | 変更が**黙って捨てられる**（エラーも出ない） |

## 2. どう解決しようとしたか

### 2-1. 考え方: 「公開・編集したときだけ作り直し、普段は作り置きを返す」

Next.js の**オンデマンド再検証**（ISR）を使う。お店に例えると次の役割分担になる。

| 役割 | 例え | 中身 |
|---|---|---|
| **Neon** | 食材庫・レシピ帳 | 記事・年表の原本。管理画面で書いた内容が入る |
| **Worker** | 料理人 | 原本を読んでページを作り、訪問者に返す |
| **R2** | 作り置きの冷蔵庫 | 作ったページ（や DB の結果）を完成品のまま保存する |
| **D1** | 「作り直し」の伝票ボード | 「このページは〇時〇分に古くなった」という記録だけを置く |

### 2-2. 流れ

```
【普段のアクセス】（ほとんどのアクセス）
訪問者 → Worker → D1「このページに作り直しの伝票は？」→ なし
                 → R2 から作り置きを返す            ※ Neon には行かない

【管理画面で公開・編集したとき】
あなた「公開」→ Server Action → Neon に保存
                              → revalidatePath / updateTag で D1 に「古くなった」と記録（伝票を貼るだけ）

【その後の最初のアクセス】
訪問者 → Worker → D1「伝票あり」→ Neon を1回読んで作り直す → R2 に保存し直して返す
（2人目以降は、また普段の流れ）
```

### 2-3. Neon に問い合わせるのと、R2 から取り出すのは何が違うか

一言でいうと、**Neon は「材料」を渡すところ、R2 は「完成品」を渡すところ**。

| | Neon（DB） | R2（ファイル置き場） |
|---|---|---|
| 置いてあるもの | 記事の原本データ（タイトル・本文・タグなどがばらばら） | 完成したページ（そのまま返せる形） |
| 1回ごとの仕事 | SQL で探して組み合わせる。そのあと Worker がページを組み立てる | ファイルを1つ読むだけ |
| 休止 | **ある**（5分アクセスがないと休止し、起きるのを待つ） | **ない** |
| 無料枠の数え方 | **起きていた時間**（月 100 CU 時間） | **読んだ回数**（月 1,000 万回） |
| 場所 | どこか1か所のサーバー（このサイトはシンガポール） | Worker と同じ Cloudflare の中 |

R2 は「ファイルを置いて取り出す」ことしかできない。検索・絞り込み・並べ替え、関係を保った編集、重複チェックは DB にしかできないので、**原本は Neon に置いたまま、作ったページだけを R2 にコピーしておく**。

### 2-4. なぜ R2 と D1 の2つが要るのか（ほかの案と比べて）

| 案 | 採用しなかった理由 |
|---|---|
| 作り置きを Neon に入れる | 結局毎回 Neon に行くので、休止・距離・無料枠の問題が残る |
| 作り置きを Cloudflare KV に入れる | 書いた内容が全拠点に届くまで最大1分ほどかかり、公開直後に古いページが見えることがある。OpenNext の公式もページの保存先には R2 をすすめている |
| 「古くなった」記録を R2 に入れる | Worker は世界中の拠点で同時に動く。書いた直後にどの拠点からも同じ内容が見える必要があり、D1 がそれに向いている |
| 完全な静的サイト（ビルド時に全部作る） | 公開のたびにビルド・デプロイが必要になる。CMS で公開してすぐ反映、ができない |
| Next.js 16 の `'use cache'` | OpenNext（Cloudflare）の公式のキャッシュのページに記載がなく、対応状況が確認できなかった。実績のある `revalidatePath` / `unstable_cache` の方式にした |
| 時間で作り直す ISR（`revalidate = 秒数`） | 公開したのに一定時間反映されない。作り直しの順番待ち（Queue）も必要になる |

### 2-5. ページの種類ごとの扱い

| ページ | 扱い | 理由 |
|---|---|---|
| 記事ページ `/{blogs,products,books}/[slug]` | **ページごと作り置き** | URL ごとに中身が決まっている。最初のアクセスで作って保存する |
| サイトマップ | **ページごと作り置き** | 公開したときだけ変わる |
| 記事一覧（タグ・ページ番号つき） | **ページは毎回作り、DB の結果だけ作り置き** | タグとページ番号の組み合わせが多く、ページごと置くと数が膨らむ |
| 年表・年表の詳細 | **ページは毎回作り、DB の結果だけ作り置き** | 年表は並び順（`?order=`）を読む。詳細は記事へのリダイレクトがある |
| 管理画面 | **作り置きしない（毎回作る）** | 常に最新が必要（1-4 の問題） |
| トップ・経歴・受賞歴・資格 | もともと静的（DB を読まない） | 変更なし |

### 2-6. slug をどうするか

slug を本当に変えられるようにしても、**公開済みの記事の URL が変わると、古い URL へのリンクが切れる**（トップページ・受賞歴にコードで書いたリンク、年表の `product_slug`、SNS や検索エンジンに載った URL）。作り置きとの兼ね合いでも、古い URL と新しい URL の両方を捨てる必要が出て複雑になる。

検討した選択肢:

1. 一度作った記事は slug を変更できないようにする
2. いつでも変更でき、古い URL から新しい URL へ移動させる（古い slug を記録する表が要る）
3. slug を保存するようにだけ直す（変えるたびにリンクが切れる）

**決定: 1。一度作った記事（下書きを含む）は slug を変更できない。**

## 3. 何が心配だったか（懸念点）と、その扱い

| 懸念 | 扱い |
|---|---|
| **作り置きを捨て忘れると、古いページが出続ける**。特にアーカイブ・下書きに戻すで忘れると、非公開にした記事が見え続ける | 捨てる処理を `src/lib/revalidatePublic.ts` の関数にまとめ、公開ページの見た目が変わる Server Action からすべて呼ぶ（4-3 の対応表） |
| 管理画面がビルド時の内容で固まる | `src/app/admin/layout.tsx` で、管理画面をすべて「毎回作る」にした |
| 無料枠（R2・D1）に収まるか | 下の見積もりのとおり、大きく下回る見込み |
| R2 の保存容量がデプロイのたびに増える | OpenNext はデプロイ（ビルド）ごとに別の場所へ保存し、古いものを自動で消さない。200 ページ × 100 KB なら1回 約 20 MB で、10 GB まで数百回のデプロイが必要。必要になったら R2 のライフサイクルルールで古いファイルを消す |
| D1 は上限を超えるとその日は使えない | 今の規模ではまず起きない（下の見積もり） |
| 公開直後の最初の1人は待つ | 作り直しの分だけ少し遅い。気になるなら、公開直後に自分で開いておく（公開後は記事ページへ移動するので、記事ページはそこで作られる） |
| 完全な静的配信ではない | Worker は毎回動く（ただし DB は読まない） |
| `pnpm preview` では本物の R2・D1 を使わない | 手元では仮の R2・D1 で動く。仕組みは手元で確かめ（5 章）、最終確認はデプロイ後 |

### 無料枠の見積もり（2026年10月時点の公式の料金ページより）

| サービス | 無料枠 | 超えたとき |
|---|---|---|
| Neon | 計算時間 月 100 CU 時間・保存 1 GB・転送 月 5 GB | 翌月まで DB が止まる（データは消えない） |
| R2 | 保存 10 GB・書き込み（Class A）月 100 万回・読み取り（Class B）月 1,000 万回・外への転送は無料 | 超えた分が課金 |
| D1 | 読み取り 1日 500 万行・書き込み 1日 10 万行・保存 5 GB | その日は D1 が使えない |
| Workers（参考） | 1日 10 万リクエスト | 無料プランではエラー |

R2 の無料枠はアカウント全体で共有（画像の配信と合算）。

1日 1,000 回の閲覧なら、R2 の読み取りは月 約 3 万回（無料枠の 0.3%）、D1 の読み取りは1日 約 5,000 行（0.1%）。1日 10 万回に増えても R2 は 30%、D1 は 10% で、先に Workers の1日 10 万リクエストに届く（これは作り置きの有無に関係ない）。

### 4-2. コードの変更

| ファイル | 変更 |
|---|---|
| `open-next.config.ts` | 作り置きの保存先を R2（`r2IncrementalCache`）、記録先を D1（`d1NextTagCache`）にした。Queue は使わない。デプロイ後に `enableCacheInterception` も追加した（8 章）|
| `wrangler.jsonc` | `NEXT_INC_CACHE_R2_BUCKET`（R2）と `NEXT_TAG_CACHE_D1`（D1）のバインディングを追加。名前は OpenNext が決めている |

| `src/db/queries/cached.ts`（新規） | 公開ページ用の、DB の結果を作り置きする関数（`unstable_cache`）。一覧・件数・ジャンルのタグ・年表。作り置きは JSON で保存され Date が文字列になって戻るので、Date に戻している |
| `src/components/PostListPage.tsx`・年表の2ページ | 上の作り置きの関数を使う。年表の `force-dynamic` を外した |
| `src/lib/revalidatePublic.ts`（新規） | 作り置きを捨てる関数をまとめた（4-3） |
| `src/app/admin/actions.ts`・`tag-actions.ts`・`history-actions.ts` | 保存・公開・アーカイブなどのあとに、作り置きを捨てる |
| `src/app/admin/layout.tsx` | `dynamic = 'force-dynamic'` で管理画面をすべて毎回作る |
| `src/app/admin/actions.ts`・`src/db/queries/select.ts` | slug の固定。更新のときは画面から送られた slug を使わず、保存済みの slug（`getPostSlugById`）を使う。新規作成のときだけ重複を確認する |
| `src/components/BlogEditor.tsx`・`InputField.tsx` | 作成済みの記事では「URLパス」を読み取り専用にし、「作成後は変更できません」と表示する。`InputField` に `readOnly` を追加 |
| （7 章）`[slug]/layout.tsx`・`history/[id]/layout.tsx` など | 存在しない URL を正しい 404 にし、記事ページをジャンルで絞る（7 章を参照）|

管理画面の一覧・編集は、作り置きの関数ではなく `select.ts` の関数を直接使う（常に最新が必要なため）。

### 4-3. どの操作で、何を捨てるか（対応表）

| 操作（Server Action） | 捨てるもの | 関数 |
|---|---|---|
| 記事の下書き保存・公開・アーカイブ | その記事のページ・記事一覧と件数（全ジャンル）・サイトマップ | `revalidatePostPages` |
| タグの作成・ジャンルへの追加/除外・並べ替え | 記事一覧と検索バーのタグ | `revalidatePostLists` |
| タグの名前・画像の変更・削除 | すべてのページ（記事ページにもタグが出るため）・記事一覧 | `revalidateAllPostPages` |
| 年表の出来事の保存・削除、ラベルの名前変更・削除 | 年表のデータ・サイトマップ | `revalidateHistoryPages` |
| 年表のラベルの作成・日記の保存 | なし（公開ページの見た目が変わらない。日記は公開ページがない） | — |

- 下書き保存でも捨てるのは、公開中の記事を下書きに戻したときに、公開ページから消すため。
- `updateTag` と `revalidatePath` は、Next.js 16 ではどちらも「すぐ古いとみなす」（`revalidateTag` に `'max'` を渡すと、古いものを見せながら裏で作り直す動きになるので使わない）。`updateTag` は Server Action の中でしか使えない。
- `revalidatePath('/', 'layout')` は、すべてのページの作り置きを捨てる。タグの変更はまれなので、記事ページの URL を1つずつ集めるより確実な方を選んだ。

### 5-2. 手元の Worker 環境（`opennextjs-cloudflare preview`）での動作

wrangler の手元の環境は、Worker が外部へ送った通信を記録できる。それを使い、1回のアクセスで Neon・R2・D1 に何回行ったかを数えた（DB は本番の Neon を読み取りのみで使用）。

| ページ | 1回目 | 2回目以降 |
|---|---|---|
| 記事ページ（`/products/syspay`） | Neon 2回 → R2 に保存（1.56秒） | **Neon 0回**、R2 から返す（0.01秒） |
| 記事一覧（`/products`） | Neon 3回 → R2 に保存（0.56秒） | **Neon 0回**（0.03秒） |
| 年表（`/history`） | Neon 1回 → R2 に保存（0.29秒） | **Neon 0回**（0.03秒） |

捨てる側は、管理画面に手元でログインできない（GitHub ログインが必要）ため、`revalidatePath` / `updateTag` が書き込むのと同じ記録を手元の D1 に直接書いて確かめた。

| 記録した内容 | 結果 |
|---|---|
| 記事ページ（`/products/syspay`）と記事一覧のデータ | どちらも次のアクセスで Neon を読み直し、その次から作り置きに戻った。記録していない年表は作り置きのまま |
| すべてのページ（`revalidatePath('/', 'layout')` と同じ記録） | 記事ページが Neon を読み直した |
| サイトマップ | Neon を読み直し、その次から作り置きに戻った |

## 7. 追加対応: 存在しない URL を正しい 404 にし、記事ページをジャンルで絞る

### 7-1. 何が問題だったか

**(1) 存在しない記事・年表の URL のステータスが 200 になる**

404 の画面と `noindex`（検索エンジンに載せない指定）は出るが、ステータスは 200 だった（いわゆるソフト 404）。原因は、[サイト全体の UI/UX 改善](./2026-10-04-site-wide-uiux.md)で記事ページ・年表に置いた `loading.tsx`。Next.js は、ヘッダーとローディング画面を**先に送り始め**、そのときにステータス 200 も送る。そのあとページ本体で記事がないと分かって `notFound()` を呼んでも、送ったステータスは変えられない。

- 検索結果には載らない（`noindex` がある）が、リンク切れのチェックツールなどはステータスを見るので見つけられない。Google からはソフト 404 として扱われる。
- Next.js はクローラーに対してページ全体を待ってから返すのでは、と考えて Googlebot・Bingbot を名乗って確かめたが、**クローラーに対しても 200** だった。

**(2) 記事ページがジャンルで絞っていない**

`getPostById` が slug だけで記事を探していたため、`/blogs/<制作物の slug>` のように違うジャンルの URL でも記事が表示された。同じ記事が2つの URL で見えるのは検索エンジン的にも望ましくなく、作り置きを入れた今は、違うジャンルの URL の分まで作り置きが作られる。

### 7-2. どう解決しようとしたか

| 案 | 内容 | 判断 |
|---|---|---|
| A. 詳細ページの `loading.tsx` を外す | 正しい 404 になる | **不採用**: 何かの理由で読み込みが遅いときの対処として、ローディング画面は残したい（依頼） |
| B. A に加えて、押したリンクに読み込み中の印を出す（`useLinkStatus`） | 反応は出せる | 不採用（ローディング画面そのものは残らない） |
| C. このままにする | — | 不採用 |
| D. ミドルウェアで先に記事があるか調べる | — | 不採用: アクセスのたびに Neon を読むことになり、作り置きの意味がなくなる |
| **E. 「記事があるか」の確認だけを、ローディング画面より手前の `layout.tsx` で行う** | `layout.tsx` は同じフォルダの `loading.tsx` より外側にあるので、送り始める前にステータスを決められる。確認には作り置きの「公開中の slug の一覧」を使い、Neon を待たない | **採用**: ローディング画面を残したまま正しい 404 になる |

(2) は、`getPostById` の条件にジャンルを加える。E の確認もジャンルごとの slug の一覧で行うので、違うジャンルの URL は 404 になる。

### 7-3. 心配だったこと

- **確認のために Neon を読むと、作り置きの意味がなくなる** → 確認には作り置きの slug の一覧（ジャンルごと）を使う。slug ごとではなくジャンルごとの一覧にしたのは、でたらめな URL へのアクセスのたびに作り置きが増えないようにするため。記事の保存・公開で一覧も捨てる（`CACHE_TAGS.posts`）。
- **Next.js は layout と並行してページ本体と `generateMetadata` も動かす** → 最初の実装では、存在しない URL のたびにページ本体が Neon に問い合わせていた（手元の確認で発見）。でたらめな URL を次々に試すクローラーが来ると Neon が起こされ続けるので、ページ本体と `generateMetadata` でも、Neon を読む前に slug の一覧で確かめて止めるようにした。年表の詳細も、形式が不正な id はページ本体で DB に問い合わせる前に止める。
- **年表の `loading.tsx` が一覧と詳細の両方を包んでいた**（`history/loading.tsx`）→ そのままでは詳細の `layout.tsx` も内側に入ってしまう。一覧を記事一覧と同じ `(list)` グループに移し（`history/(list)/page.tsx`・`loading.tsx`）、詳細には専用の `history/[id]/loading.tsx` を置いた。URL は変わらない。

## 8. デプロイ後の確認と、見つかった問題（記事ページが新しい Worker で作り直されていた）

### 8-1. デプロイ

`pnpm run deploy` で、R2 へのビルド済みページの書き込み（24 件）と D1 の表（`revalidations`）の作成が行われ、デプロイが完了した。

### 8-2. 本番で見つかった問題

本番で記事ページを何度か開くと、応答ヘッダーが `x-nextjs-cache: HIT` のときと `STALE`（古い）のときがあった。手元で「作り置きを作る → サーバーを再起動して新しい Worker で受ける」を再現すると、次のことが分かった。

- 新しい Worker が作り置き済みの記事ページを受けると `STALE` と判定し、**その場でページを作り直して Neon を2回読んでいた**
- 裏での作り直しの依頼は、queue を設定していないので「Dummy queue is not implemented」のエラーで捨てられていた

**原因**: 記事ページは最初のアクセスで作るページ（ビルド時には作らない）。Next.js はこうしたページの「有効期限なし」を、作った Worker のメモリにしか持たない。ほかの Worker では期限が分からず、既定の「1秒」とみなして古いと判定していた（Next.js の `SharedCacheControls` / `calculateRevalidate`）。Cloudflare の Worker は短い間隔で入れ替わり、拠点も多いので、このままでは記事ページで Neon への問い合わせがかなり残る。

### 8-3. 対処

`open-next.config.ts` に `enableCacheInterception: true` を追加した。作り置きのあるページは Next.js に渡す前に OpenNext が返す。OpenNext は作り置きに保存された期限（なし）で判定するので、古いと判定されない。Next.js を動かさずに返せるので、Worker の処理も軽くなる。PPR を使う場合は使えない設定だが、このサイトでは使っていない。

検討したほかの案:

| 案 | 判断 |
|---|---|
| queue を設定して、裏での作り直しを動かす | 不採用。古いと誤判定されるたびに作り直して Neon を読むことになり、問題が悪化する |
| ビルド時に全記事を作る（`generateStaticParams` で全 slug を返す） | 不採用。ビルド後に公開した記事は同じ問題が残り、ビルドが DB に依存する |

### 8-4. 確かめたこと（手元の Worker 環境）

| 状況 | 記事ページ | 一覧 | 年表 | サイトマップ | 存在しない記事 |
|---|---|---|---|---|---|
| 作り置き済み・同じ Worker | Neon 0回 | 0回 | 0回 | 0回 | 404・0回 |
| 作り置き済み・**新しい Worker**（再起動後） | **Neon 0回**（以前は2回）| 0回 | 0回 | 0回 | 404・0回 |
| 記事ページ・一覧・サイトマップを「古くなった」と記録した後 | 1回だけ作り直し、次から 0回 | 同左 | 記録していないので 0回 | 同左 | — |
| すべてのページを「古くなった」と記録した後（`revalidatePath('/', 'layout')` と同じ） | 1回だけ作り直し、次から 0回 | — | — | — | — |

作り直しのエラー（Dummy queue）も出なくなった。

## 元に戻すとき

`open-next.config.ts` の `incrementalCache` と `tagCache` を外して（`wrangler.jsonc` のバインディングも外して）デプロイすれば、作り置きのない元の動きに戻る。R2 バケットと D1 は、不要なら Cloudflare のダッシュボードか `wrangler r2 bucket delete` / `wrangler d1 delete` で消せる。
