## 1. デプロイ直後の作り置きの温め（6）

**問題**: OpenNext はビルドごとに別の場所（`incremental-cache/<ビルドID>/`）へ作り置きを保存する。デプロイすると作り置きはすべて空になり、デプロイ直後は各ページの最初のアクセスが遅い（ページの組み立て＋Neon の読み込み）。

**採用しなかった案**: ビルド ID を固定して、作り置きをデプロイをまたいで使い続ける案。古い作り置きの HTML は、前のビルドの JavaScript ファイル（ファイル名にハッシュが付いている）を参照しているので、デプロイ後に画面が壊れる。

**対処**: [`scripts/warm-cache.mjs`](../scripts/warm-cache.mjs) を作り、`pnpm run deploy` の最後に自動で実行するようにした（単独では `pnpm warm-cache`）。

- サイトマップに載っているページと、記事一覧・年表（`?order=newest` を含む）を、4件ずつ並行して開く
- 5xx のときは1回だけやり直す。失敗があっても、デプロイ自体は終わっているので終了コードは 0（デプロイの失敗と区別するため）
- R2 はどの拠点の Worker からも読めるので、どこから開いても全拠点の訪問者に効く
- 自動生成のサムネイル（`/api/og`）と画像（`/api/images`）は、Cloudflare の拠点ごとのキャッシュなので温めない（スクリプトを動かした拠点にしか保存されない）

**注意**: 温めはページの組み立てを一度に行うので、**無料プランでは CPU 時間の上限で打ち切られやすい**。有料プランにしてからデプロイする。

## 2. R2 の古い作り置きの自動削除（7）

**問題**: 古いビルドの作り置きは自動では消えず、デプロイのたびに増える（手元でも、ビルドごとに約35件ずつ残っていた）。

**対処**: 本番の作り置きのバケット `wadawataru-me-cache` に、R2 のライフサイクルルールを追加した（コードではなく Cloudflare 側の設定）。

```bash
npx wrangler r2 bucket lifecycle add wadawataru-me-cache expire-old-incremental-cache incremental-cache/ --expire-days 30 --force
npx wrangler r2 bucket lifecycle list wadawataru-me-cache   # 確認
```

- `incremental-cache/` 以下のオブジェクトを、作られてから30日で削除する
- 今のビルドの作り置きも30日で消えるが、消えたページは次のアクセスで作り直されるだけ（月に1回、ページごとに Neon を1回読む程度）
- **確かめたこと**: 手元で今のビルドの作り置き（35件）をすべて消してから各ページを開き、トップ・経歴・受賞歴・資格・サイトマップ・記事・一覧・年表がすべて 200 で表示され、存在しない記事は 404 のままだった

## 3. 404 のページを R2 に保存しない（10）

**問題**: 記事ページは「最初のアクセスで作って保存する」ので、存在しない URL（`/blogs/でたらめ` など）へのアクセスでも、404 のページが URL ごとに R2 に保存されていた。でたらめな URL を試すクローラーが来ると、R2 の書き込み回数と保存容量を使い続ける。

**対処**: [`open-next.config.ts`](../open-next.config.ts) で、R2 の作り置きの保存処理を包み、ステータスが 404 のページだけ保存しないようにした（`r2IncrementalCacheWithoutNotFound`）。

- 記事があるかの確認は、作り置きの slug 一覧（Neon を読まない）で行うので、404 を保存しなくても毎回 404 を返すだけで済む
- 公開中の記事をアーカイブしたときは、作り置きを捨てる記録（D1）があるので、古い 200 のページが返ることはない
- **確かめたこと**: 手元で存在しない URL を3種類開いても、R2 の作り置きは1件（slug 一覧）しか増えなかった。2回目以降も 404 のまま

## 4. 画像を Cloudflare の拠点にキャッシュする（9）

**問題**: `/api/images` は `Cache-Control: public, max-age=31536000, immutable` を返しているが、Workers のレスポンスは Cache API を明示的に使わない限り拠点にキャッシュされない。初めて見る人には毎回 Worker と R2 が動いていた。

**対処**: [`src/app/api/images/[key]/route.ts`](../src/app/api/images/[key]/route.ts) で、自動生成のサムネイル（`/api/og`）と同じく Cache API（`caches.default`）を使うようにした。

- 先に拠点のキャッシュを見て、あればそのまま返す
- なければ R2 から読んで返し、返した後に拠点のキャッシュへ保存する（`waitUntil`。保存を待たずに画像を返せる）
- キーは中身が書き換わらない（`{タイムスタンプ}-{ランダム}.{拡張子}`）ので、期限まで保存し続けてよい
- 404 はキャッシュしない
- **確かめたこと**: 手元の R2 にテスト用の画像を置いて3回開くと、R2 を読んだのは1回目だけだった。2回目以降も `Content-Type`・CSP（`sandbox`）・`Cache-Control` のヘッダーはそのまま

Worker 自体は毎回動く（拠点のキャッシュを見るため）が、R2 の読み取り回数と待ち時間が減る。

## 5. サイトマップから、記事へ移動するだけの年表の URL を外す（ついでに見つけた問題）

**問題**: 温めのスクリプトを動かして気づいた。サイトマップに、記事にリンクしている年表の出来事の個別ページ（`/history/<id>`）が載っていた。これらは記事へ 307 で移動するだけなので、検索エンジンにとって無駄な URL になる（記事の URL は別に載っている）。

**対処**: [`src/app/sitemap.ts`](../src/app/sitemap.ts) で、記事にリンクしている出来事（`productSlug` がある）を外した。今のデータでは、詳細のある出来事はすべて記事につながっているので、サイトマップの `/history/<id>` は 0 件になる。
