# 2026-10-04 制作物の画像が極端に遅い問題（GitHub 画像の R2 移行と WebP 変換）

- 対応日: 2026-10-04
- 対象: 制作物の記事・一覧のサムネイル・年表の画像、管理画面の画像アップロード

## 概要と原因

### 症状

制作物の記事を開くと、本文の画像がなかなか表示されない。

### 原因: 画像を GitHub に置いていた

制作物の記事の画像（本文とサムネイル）は、自前の R2 ではなく、**GitHub の `user-attachments`**（README や Issue に画像を貼ったときに作られる URL）を参照していた。ここに、悪い条件が3つ重なっていた。

1. **ファイルが大きい**: スクリーンショットを無圧縮の PNG のまま使っていた。1枚で最大 4.5MB。
2. **配信元が遠い**: GitHub の URL は 302 でアメリカの AWS S3 にリダイレクトされる。日本からだと、最初のデータが届くまで約1秒かかり、その後の転送も遅い。
3. **キャッシュされない**: リダイレクトが `cache-control: no-cache` で、転送先の URL には **5分で切れる署名**（`X-Amz-Expires=300`）が付いている。開くたびに URL が変わるので、ブラウザのキャッシュが効かず、毎回ダウンロードし直していた。

本番での実測（移行前）:

| 記事 | 画像の大きさ | 読み込み時間 |
|---|---|---|
| bingo2 | 373KB | 3.2秒 |
| entry-system | 499KB | 4.1秒 |
| gesture-audio | 2,528KB | 16.7秒 |
| lovely-stick | 4,512KB | 19.0秒 |

さらに調べると、**サムネイルも GitHub の画像**だった。サムネイルは制作物の一覧ページのカードと年表にも表示されるので、一覧ページや年表の画像が遅いのも同じ原因だった。

自前の R2 に置いていた画像（`/api/images/...`）は 0.3〜0.45秒程度で、問題になる遅さではなかった。

## 放置するとどうなるか

- 記事の画像が出るまで十数秒かかり、訪れた人は画像を見ないままページを離れる。ポートフォリオで成果物を見せるための画像なので、致命的になる。
- 開くたびに数 MB をアメリカから取り直すので、スマートフォンの通信量も無駄に使わせる。
- GitHub の添付画像は、外部サイトに配信するための仕組みではない。リポジトリの公開設定や GitHub の仕様が変われば、予告なく表示されなくなる恐れがある。

## どう対処したか

### 1. 管理画面からアップロードする画像を、すべて WebP に変換する

[`src/lib/convertToWebp.ts`](../src/lib/convertToWebp.ts) を作り、[`uploadImage()`](../src/lib/uploadImage.ts) の中で、送信前に変換するようにした。管理画面の画像アップロード（記事の本文・サムネイル、年表、タグ画像）はすべて `uploadImage()` を通るので、**どの画面から上げた画像にも漏れなく効く**。

| 項目 | 設定 | 理由 |
|---|---|---|
| 形式 | WebP・品質 0.85 | 下の比較のとおり、見た目はほぼ変わらずに大幅に小さくなる |
| 大きさ | 長い辺が 1920px を超えるときだけ、比率を保って縮小する | 記事の表示幅に対して十分。小さい画像は拡大しない |
| 透過 | 保つ | WebP は透過を扱える。タグ画像の透明な余白もそのまま残る |
| 変換しない形式 | SVG・GIF・WebP | SVG はベクター画像で劣化する。GIF はアニメーションが止まる。WebP は再変換で劣化が重なる |
| 変換できなかったとき | 元の形式のまま送る | WebP を書き出せないブラウザ（古い Safari など）や、ブラウザが読めない形式（HEIC など）のため。受け付けるかどうかはサーバー側の形式判定に任せる |

**変換をブラウザ側で行う理由**: Workers には画像処理ライブラリがなく、CPU 時間の制限も厳しい。Cloudflare Images を使う方法もあるが、変換の料金が発生しうる。ブラウザの canvas なら、追加の依存も費用もなく変換できる。

**品質 0.85 にした理由**（移行対象の画像4枚で比較）:

| 画像 | 元の PNG | 0.85 | 1.0 | 可逆（lossless） | PSNR（0.85 / 1.0） |
|---|---|---|---|---|---|
| 1（889×1485） | 373KB | 63KB | 139KB | 218KB | 33.9 / 34.1 dB |
| 2（1553×900） | 499KB | 96KB | 201KB | 239KB | 36.5 / 36.8 dB |
| 3（→1920×1080） | 2,528KB | 52KB | 140KB | 484KB | 36.8 / 36.9 dB |
| 4（→1920×1007） | 4,512KB | 183KB | 491KB | 1,472KB | 37.9 / 38.9 dB |

品質を 1.0 にしても、PSNR（元画像への近さ）はほとんど上がらず、大きさは約 2.5倍になる。非可逆の WebP は、品質の設定に関係なく色の情報を縦横半分の解像度で保存する（色差の間引き）ため、品質を上げても画質は頭打ちになる。文字の多い部分を切り出して並べても、0.85 と 1.0 の違いは目で見分けられなかった。

**確認したこと**: ヘッドレスの Chrome で `convertToWebp` を実行し、次のとおり動くことを確かめた。

| 入力 | 結果 |
|---|---|
| 4.6MB の PNG（2167×1136） | WebP 172KB・1920×1007（比率を保って縮小） |
| 半透明の PNG | WebP になり、透過も保たれた（不透明度 0.3 → 77/255） |
| SVG | 変換されず、そのまま |

### 2. GitHub の画像を R2 に移し、URL を置き換える

[`scripts/migrate-github-images.mjs`](../scripts/migrate-github-images.mjs) を作って実行した。

- **探す範囲**: `posts_table`（本文・サムネイル）、`history_events_table`（本文・サムネイル）、`tags_table`（画像）。下書き・アーカイブの記事も含む。
- **変換**: 1 と同じ設定（長い辺 1920px・比率維持・品質 0.85）で、sharp を使って WebP にする。sharp は Next.js の依存として入っていたものを、スクリプトから使えるよう開発用依存に追加した。
- **進め方**: 既定は**下見（読み取りのみ）**で、`--apply` を付けたときだけ書き込む。下見の結果を確認してから実行した。
- **安全策**:
  - 書き換える前に、対象の行を `backups/` に JSON で保存する（このフォルダは `.gitignore` に入れた）。
  - DB の書き換えは1回のトランザクションで行う。途中で失敗したら、どの行も書き換わらない。
  - 画像の取得・変換に1件でも失敗したら、何も書き込まずに中止する。
  - 記事の `updated_at`（最終更新日）は変えない。画像の置き場所を移しただけで、記事の内容は更新していないため。
- **元データの置き換え**: 以前の記事投入スクリプトの元データ（`scripts/data/product-articles.mjs`）の URL も置き換えた。そのスクリプトを再実行しても、GitHub の URL に戻らないようにするため。

**実行結果**:

| 記事 | 本文の画像 | サムネイル |
|---|---|---|
| lovely-stick | 4,512KB → 183KB | 140KB → 25KB |
| gesture-audio | 2,528KB → 52KB | 894KB → 64KB |
| bingo2 | 373KB → 63KB | 518KB → 144KB |
| entry-system | 499KB → 96KB | 499KB → 96KB |
| 23bit-adder | — | 1,179KB → 289KB |
| chicken-shooting | — | 3,585KB → 113KB |

- 画像 10 枚、合計 **14.7MB → 1.1MB**（約 1/13）
- DB の更新は 12 行（制作物の記事 6 件と、同じ画像を使っている年表の出来事 6 件）
- バックアップ: `backups/github-images-2026-10-03T15-52-35-874Z.json`（手元のみ）

## 確認したこと（本番）

| 確認 | 結果 |
|---|---|
| 移行スクリプトの下見をもう一度実行 | 「GitHub の画像 URL は見つかりませんでした」 |
| 制作物の記事6件・一覧・年表の HTML | GitHub の URL は 0 件 |
| 記事内の画像の読み込み時間 | **3〜19秒 → 0.37〜0.58秒** |
| 一覧・年表のサムネイル | 0.26〜0.9秒。すべて `image/webp` |

## 元に戻す方法

DB は `backups/` の JSON に、書き換え前の行がそのまま入っている。各行の `content`・`thumbnail`（タグは `image_url`）を、この値で `update` し直せば元に戻る。GitHub 上の元の画像は消していない。R2 に置いた WebP は残るが、参照されなくなるだけで害はない。

## 残っていること

- **WebP 変換（1）は、デプロイして初めて本番の管理画面に反映される**（DB と R2 の移行（2）は、実行した時点で本番に反映済み）。デプロイ後、管理画面で PNG を貼り付けて、`.webp` の URL が挿入されることを確かめる。
- **画像配信のエッジキャッシュ**: 今は同じ人のブラウザのキャッシュしか効いていない（[一覧ページの記録](./2026-10-04-list-page-loading.md#残っていること関連して分かったこと)を参照）。初めて見る人にも速く届けるには、`/api/og` と同じく Cache API を使う必要がある。
